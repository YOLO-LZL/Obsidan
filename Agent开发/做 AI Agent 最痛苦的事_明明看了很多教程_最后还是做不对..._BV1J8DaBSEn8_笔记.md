# AI Agent 架构演进：实践中的迭代与反思

## 背景与核心痛点

UP 主在过去 3 个月开发了一个用于生成讲解视频动画效果的 AI Agent。在搭建第一版时，采用了标准的 **Plan and Execute（规划-执行）架构**：

- 主 Agent 负责 Action Layer（整体编排）
- 拆分为多个子 Agent（Design Agent、Coding Agent）

**两个绕不过去的问题：**

1. **小改动成本太高**：只想改一行代码，Agent 仍要走完整流程（主 Agent → 分发 → 子 Agent → 执行），架构在任务变小变细时显得过于笨重

2. **主 Agent 越权**：设计要求主 Agent 只负责编排，不自己动手修改代码，但实际运行时主 Agent 经常"忍不住"动手修改，无论如何在 System Prompt 中强调职责边界都没有用

## 第一次顿悟：Plan-Execute 不是架构模板

### 从开源项目得到的启发

UP 主去查看真实工业环境中已经成功的产品架构（如 OpenCode 的 Agent 体系），发现架构和想象中的"标准答案"不一样：

- OpenCode 的主 Agent **既能够写代码，也能够进行编排**
- 子 Agent 依然可以做代码编写
- 并没有严格的 Plan-Execute 分层

### 问题的本质

**Plan and Execute 是 Agent 工作的一种方式，而不是必须按特定方式切分组织架构的模板。**

UP 主总结了自己犯的"架构强迫症"：

> 我们太容易自动把 Plan-Execute 翻译成一种很具体的系统形态——必须有 Planner、必须有 Executor，两个组件之间切得工整清晰。

### 关键认知转变

- Plan and Execute 是工作流程的抽象概念
- 不是说你必须创建一个 Planners + Executors 的组织架构
- **没有人规定主 Agent 和子 Agent 不能有功能重叠**

## 第二次迭代：Skill 动态注入

### 触发点

Killot 概念的流行——提示词的动态注入：当 Agent 在某个阶段需要某种能力时，把对应的 Skill 塞到上下文里。

### 实验

将原来 Design SubAgent 和 Coding SubAgent 的 System Prompt 原封不动变成 Skill，在原来调用这些 SubAgent 的地方，不再新起 SubAgent，而是直接注入对应 Skill。

### 结果

- 整体性能没有下降
- 复杂任务中性能反而有提升
- Token 开销变小

### 原因分析

**砍掉了主 Agent 和子 Agent 中间那一层的通信成本。**

原本需要解决的问题：
- 如何让 SubAgent 看到用户传入的图片
- 如何把中间搜索结果传给子 Agent

使用 Skill 后：
- 全程只有一个 Agent 在工作
- Agent 天然知道前面几步发生了什么
- 天然继承上下文，不再需要额外设计"如何传递信息"

### 真正的领悟

> 不是 Skill 替代了 SubAgent，而是 Skill 暴露了一件事：**最初的 SubAgent 架构本身就是冗余设计**。

## 长任务（Long Running Task）挑战

当系统需要连续生成上百段代码、上百帧内容时，问题变得更加复杂。

### 第一次尝试：加入 To-Do List

预期效果：让 Agent 在生成时知道自己做到哪一步了，逼着它按顺序执行。

### 实际跑起来后出现的三个症状

| 症状 | 表现 |
|------|------|
| **步骤合并/跳过** | 到靠后阶段，Agent 把本应分开做的内容合在一起做（如第 80-85 段一起生成、第 90-100 段一起生成），像在"赶工" |
| **规则失效** | 最初在 Skill 中写好的规则（风格、控制流程等），越到后面越不听 |
| **输出同质化** | 前面几段代码还能看出区别，后面就变成复制前面某段、只改几个字/颜色就交差 |

## 底层原因：上下文注意力分布

### 核心原理

大模型对上下文中不同位置的信息**并非平均对待**：

- **注意力最强**：
  1. 前面的 System Prompt
  2. 离当前输出最近的那段内容

- **注意力最弱**：中间一大段信息，尤其是上下文越来越长后

### 这解释了所有症状

**规则失效的原因**：
- 不是模型"忘了"规则，而是规则被埋在前面 99 步产生的大量内容下面
- 模型不是忘了，而是**不再优先注意它**

**赶工的原因**：
- 当上下文越来越长、越来越接近上限时
- 模型自然表现出**压缩输出、减少细节**的倾向
- 这是它从训练中得来的默认行为

### 关键结论

> Context Engineering 不是往里面塞更多信息，而是**把真正重要的信息放到模型更容易注意到的位置上**。

## 解决方案：Reatement 机制

### To-Do List 真正有效的地方

To-Do List 的价值不在于"记录"，而在于**在执行过程中不断重复任务**：

```text
不断重复：我现在做到哪一步了，下一步是什么
```

这个动作的本质：**把下一步任务重新放回到离当前生成最近的地方**——也就是模型注意力最强的地方。

### Reatement 的正确理解

| 情况 | 正确做法 |
|------|---------|
| To-Do List 创建后静静放在开头，后面不再提 | 几乎不会发挥作用 |
| 持续性在上下文中重提任务 | 真正发挥作用 |

> 在长任务里，**适当的重复、适当的"废话"，很多时候不是浪费，而是必要的控制手段**。

### KV Cache 的工程约束

**模型处理上下文的工作机制**：
- 已计算的部分会被缓存（KV Cache）
- 新增内容只需计算增量
- 如果修改了前面的内容（如 System Prompt 中改了哪怕一个字），从改动位置开始后面的缓存链都要重新计算

**实际工程中的信息分类**：

| 类型 | 定义 | 放置位置 | Reatement 方式 |
|------|------|----------|---------------|
| **静态规则** | 所有任务都适用、不会变的东西（如代码风格、输出格式） | System Prompt | 无需重复，始终可见 |
| **动态信息** | 计划、To-Do List、Skill | 上下文最尾端 | 在最新生成内容后面追加重提 |

### 双重 Reatement

不仅要告诉模型"下一步是什么"，还要反复提醒"下一步得怎么做"：

- 只 Reatement To-Do List 的步骤 → 模型只知道进度
- 同时 Reatement Skill 中的关键规则 → 模型记得执行方式

这就是为什么记忆系统里通常不仅有 To-Do List，还有 Findings、Plan。

## 第三次迭代：SubAgent 的必要回归

### 问题的本质变化

之前解决的是"该看到的信息没被看到"（通过 Reatement 解决）。

现在要解决的是**"不该看到的信息被看到了"**——代码同质化的原因：

- 第一段代码用了某个框架
- 后面的代码就觉得"前面这样写一定有道理，照着写就行"
- 虽然带来一致性、减少出错，但失去了创意属性

### 新 SubAgent 的定位

这一次 SubAgent 回来，解决的是**上下文隔离**的问题：

- 在某些任务里，给任务一个干净的上下文窗口
- 让局部任务有独立思考的机会
- **可以屏蔽掉不该让它看到的内容**（如之前已生成的代码结果）

### SubAgent 机制的进化

| 版本 | SubAgent 的意义 |
|------|----------------|
| **最初版本** | 冗余设计，是架构强迫症的产物 |
| **Skill 替代后** | 去掉后系统更轻、更顺、更便宜 |
| **第三次加回** | 必要的上下文隔离工具，是上下文管理策略的核心组成 |

**形式上回到了主 Agent 做 Planning、子 Agent 做 Execution 的双层架构，但背后的依据完全不同。**

## 核心心法

### 1. 从问题出发，而非从架构出发

> 真正决定系统为什么会出现问题，不是记忆系统、验证系统这些名词本身，而是**弄清楚症状背后的底层原因**。

### 2. 架构没有标准答案

- OpenCode 的主 Agent 既写代码又编排 → 没人规定不能这样
- Skill 替代 SubAgent 后又加回来 → 形式不重要，解决问题才重要
- **真实有效的架构，都是迭代出来的，不是设计出来的**

### 3. Reatement 是核心控制手段

```
Reatement 的本质 = 把重要信息推送到模型注意力最强的位置
```

| 信息类型 | 注意力位置 | 处理方式 |
|----------|------------|----------|
| 静态规则 | System Prompt | 一次写入，持续生效 |
| 动态信息 | 上下文尾端 | 周期性追加重提 |

### 4. 工具是为问题服务的

- Skill 是工具，SubAgent 是工具，Harness 是工具
- **不是用了某个热门框架就代表系统先进**
- 永远问自己：**我的系统真的需要这个东西吗？**

## 实用工程建议

| 场景 | 建议 |
|------|------|
| **小任务/简单任务** | 单 Agent 一撸到底即可，不必引入复杂架构 |
| **需要校验/独立判断** | 独立 LLM（独立 Agent）是必须的 |
| **长任务** | 周期性地 Reatement To-Do + 关键规则，控制在上下文尾端 |
| **上下文即将爆满** | 考虑拆分任务，或启动 SubAgent 提供干净上下文 |
| **防止同质化** | 需要局部上下文隔离时，SubAgent 重新派上用场 |
| **信息放置** | System Prompt 放静态规则，动态信息用追加重提 |
